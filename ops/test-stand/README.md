# LDAP и права доступа на тестовом стенде

Рабочий исходный код: `/Users/kirillkolomoec/Documents/api-main`.
Стенд: https://37.235.241.58. Исполнитель на стенде — заглушка: реальные файлы не передаются.

## Подключение домена

Администратор открывает **Настройки → LDAP**. Укажите адрес контроллера, корневой DN, DN служебной учётной записи и её пароль. Для AD оставьте идентификатор `objectGUID`, логин `sAMAccountName`; фильтр пользователей ограничивает допустимые учётные записи. Проверка отключения AD выполняется по `userAccountControl` дополнительно к фильтру активности. Для обычного LDAP задайте постоянный уникальный атрибут идентичности и фильтр активности согласно схеме каталога.

Поддерживаются LDAPS (`ldaps://…`) и StartTLS (`ldap://…`). Сертификат сервера и его имя проверяются. Корпоративный CA необходимо добавить в доверенное хранилище JVM; при отдельном хранилище задайте `javax.net.ssl.trustStore` и соответствующий пароль через защищённую конфигурацию запуска. Не отключайте проверку сертификата. Кнопка проверки использует введённые, ещё не сохранённые поля; синхронизация использует сохранённую конфигурацию.

Пароль служебной учётной записи не возвращается в API. Пустое поле при сохранении сохраняет прежний пароль. Значение шифруется AES-GCM ключом `FDE_LDAP_ENCRYPTION_KEY` (32 случайных байта в Base64). Ключ хранится отдельно от БД в Kubernetes Secret `fde-ldap`; на стенде исходный файл находится в `/home/fdeadmin/fde/deploy-20261026/ldap-secret.env` с правами 600. Сохраните ключ вместе с защищённой резервной копией: без него прежний пароль расшифровать нельзя.

После первого успешного доменного входа пользователь появляется в БД без ролей и видит страницу описания панели. Администратор назначает ему роли в управлении доступом. Существующая локальная учётная запись не связывается автоматически с одноимённой доменной. После создания доменных пользователей нельзя заменять каталог, корневой DN, тип каталога и атрибут идентичности через форму: это требует отдельной миграции идентичностей.

## Проверка и блокировка учётных записей

Включите синхронизацию и задайте интервал (1–1440 минут). Планировщик проверяет необходимость запуска раз в минуту. Можно запустить проверку вручную и посмотреть статус, время и счётчики последней попытки. Проверяются уже зарегистрированные доменные пользователи, а не импортируется весь AD.

Отключённая или удалённая учётная запись деактивируется; ранее выданные access/refresh-токены перестают приниматься. Локальные пользователи не затрагиваются. Ручная блокировка администратором сохраняется после последующих синхронизаций. Недоступность каталога, неполный результат или превышение срока проверки приводят к ошибке без частичного применения изменений. Сбор результатов ограничен 20 секундами и 10 000 зарегистрированных доменных пользователей; поиск выполняется пакетами по 100 идентификаторов через одно TLS-соединение. Для большего числа зарегистрированных пользователей потребуется изменить лимиты и схему фонового выполнения.

## Роли и потоки

Предустановлены DWH, PC, OFD, PI, LKPP, SDP: чтение потоков и сессий своего клиента. Совпадение кода точное, без учёта регистра и крайних пробелов: DWH соответствует источнику **или** получателю DWH, но не DWH-TEST. Несколько ролей объединяют доступные коды клиентов. Дополнительные ограничения RLS продолжают действовать.

Для новой роли администратор задаёт код, название, коды клиентов и разрешения интерфейса/API. Коды клиентов определяют область данных, разрешения — допустимые действия. Пустой список клиентов не даёт доступа к потокам. ADMIN видит все потоки и управляет настройками LDAP. Проверки доступа выполняются сервером, включая прямые ссылки, сессии, файлы, запуск и расписания.

## Проверка и выпуск

Локальные проверки (Java 17, Node 22):

```sh
mvn -DskipUI=true test
cd ui
npm ci
npm test -- --run
npm run build
```

Если синхронизация каталога Documents создаёт дубли результатов сборки, используйте отдельный временный каталог: `mvn -DskipUI -Dfde.build.directory=/private/tmp/fde-api-build test`. Исходники по-прежнему читаются из репозитория.

Передайте архив исходников без `.git`, `node_modules`, `target`, сертификатов и файлов секретов в отдельный каталог релиза на сервере. Из этого каталога выполните:

```sh
bash ops/test-stand/deploy-release.sh UNIQUE_RELEASE_TAG
python3 ops/test-stand/smoke_access.py https://37.235.241.58 /home/fdeadmin/fde/deploy-20261026/credentials.json
```

Сценарий выпуска собирает интерфейс и API, сохраняет дамп БД и предыдущую конфигурацию Deployment, добавляет ключ шифрования и обновляет образ API. Архивы находятся в `/home/fdeadmin/fde/deploy-20261026/backups`. Проверка доступа создаёт помеченные QA-потоки и роль, а тестовых пользователей деактивирует в конце. Она предназначена для этого тестового стенда.

После выпуска проверьте вход, страницу настроек и управление ролями в браузере. Настоящее подключение к AD проверяется только после ввода реальных реквизитов каталога и установки его CA.
