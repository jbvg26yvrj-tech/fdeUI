# Доменный вход, синхронизация AD и доступ к потокам

Дата: 26 октября 2026. Репозиторий: /Users/kirillkolomoec/Documents/api-main.
Статус: проект решения для проверки пользователем; реализация ещё не начата.

## Цель и согласованные требования

Обновить страницу входа. Добавить доменную авторизацию LDAP/AD и пункт «Настройки → LDAP», доступный только ADMIN. При первом успешном доменном входе автоматически создавать локальную запись пользователя без ролей. Администратор назначает права вручную. Пользователь без функциональных прав видит только описание FDE и может выйти из системы. Синхронизация AD деактивирует учётки отключённых/удалённых сотрудников.

Добавить роли DWH, PC, OFD, PI, LKPP, SDP и сохранить возможность ADMIN создавать новые роли. DWH ограничивает видимость потоками, у которых источник или получатель — DWH.

## Выбранный подход

Расширить существующий Spring Boot API, JWT-вход и модель ролей. Отдельный сервис идентификации для этой задачи не нужен. Существующее управление ролями остаётся основным интерфейсом назначения доступа; не вводим параллельную систему ролей. Только JSON-фильтра таблицы недостаточно: единая серверная политика должна защищать все способы чтения и изменения потока.

Образец жизненного цикла — Mattermost: создание при первом входе, периодическая синхронизация ранее вошедших пользователей, деактивация с отзывом сессий. Не копируем несвязанные функции Mattermost или его требования к email.
Источник: https://docs.mattermost.com/administration-guide/onboard/ad-ldap

## Учётные записи и вход

- Явные способы входа: локальный и доменный. LDAP показывается только после включения администратором. Не переключаться автоматически на локальный пароль при ошибке LDAP.
- Верификация доменного пароля выполняется через LDAP bind по найденному DN. Пустой пароль запрещён, параметры поиска экранируются, результат должен однозначно определять пользователя.
- Сохранять источник учётной записи и стабильный идентификатор каталога: objectGUID для AD, entryUUID для совместимого LDAP. Логин не используется как неизменяемый ID.
- При первом успешном входе активного сотрудника создавать активную запись без ролей и без требования смены локального пароля. Одновременные первые входы не должны создавать дубликаты.
- Пароль сотрудника не сохранять. Локальную запись с совпавшим логином автоматически не связывать с доменной: конфликт требует разрешения администратором.
- Переименование доменного логина не должно менять UUID пользователя или его назначенные роли.
- Локальный администратор сохраняет независимый доступ. Изменение доменного пароля выполняется вне FDE.
- JWT-фильтр и обновление токенов проверяют актуальную активность пользователя. Деактивированный пользователь не продолжает работу со старым access token.

## Синхронизация

- Настраиваемый интервал, первоначально 15 минут, и кнопка «Синхронизировать сейчас».
- Проверять только пользователей, уже созданных при доменном входе; не импортировать весь каталог.
- Для AD учитывать отключение через userAccountControl и срок действия учётки; отсутствие в успешно проверенной области поиска также означает деактивацию. Для общего LDAP нужен настраиваемый фильтр активных пользователей.
- Недоступность AD, таймаут, ошибка прав или неполный ответ не считаются увольнением. Не выполнять массовую деактивацию по ошибке соединения/поиска.
- Сначала получить и проверить результаты, затем применить изменения. Не допускать наложения ручной и фоновой синхронизации; координировать запуск через БД для нескольких экземпляров API.
- При деактивации отзывать refresh tokens; новые API-запросы блокируются проверкой актуального состояния учётки. Данные и назначенные роли сохраняются.
- Причину неактивности хранить отдельно. Синхронизация может восстановить активность после отмены отключения в AD, но не отменяет ручную блокировку администратора FDE.
- В настройках показывать время и итог последней попытки, количество проверенных/обновлённых/деактивированных пользователей и безопасное сообщение ошибки. Пароли не журналировать.
- Гарантия отключения: после следующей успешной синхронизации, а не мгновенно в момент изменения AD. Повторный доменный вход также проверяет состояние каталога.

## Роли и ограничения потоков

Предлагаемая точная трактовка правила, подлежащая проверке пользователем:

- `clientFrom = DWH OR clientTo = DWH`. Сравнение полного кода, без учёта регистра и внешних пробелов; DWH-TEST не является DWH.
- Для PC, OFD, PI, LKPP и SDP действует такое же правило по соответствующему коду.
- Несколько ролей объединяют доступные коды: DWH + PC дают потоки с любым из этих участников.
- Предустановленные роли предоставляют просмотр своих потоков и связанных сессий. Создание, редактирование, удаление, запуск, остановка и расписания — отдельные права, которые назначает ADMIN.
- ADMIN видит все потоки и управляет настройками/пользователями/ролями.
- Для новых ролей в существующей форме добавить поле «Доступные клиенты». Пустая область не даёт доступа ко всем потокам. Название роли само по себе не расширяет доступ.
- Функциональные права и область данных проверяются совместно. Существующие дополнительные RLS-ограничения сужают область, а не расширяют её. Ошибка вычисления обязательного ограничения запрещает доступ.
- Ограничение применяется до пагинации к спискам и итоговым количествам. Карточка потока, его задачи, связанные сессии, расписания, запуск и остановка проверяют тот же доступ на сервере.
- Изменение участников потока требует доступа и к исходной, и к новой области. Массовые операции также проверяются на сервере; запрещённые действия не должны частично применяться.
- Без прав — информационная страница. При прямом запросе защищённых API возвращается отказ; скрытие меню не является проверкой доступа.

## Настройки LDAP

ADMIN на UI и на API. Поля: включение входа и синхронизации, адрес/порт, LDAPS или StartTLS, базовый DN, DN служебной учётки и пароль, фильтр пользователей, атрибуты логина/стабильного ID/имени/email, фильтр активности, интервал и таймауты. AD имеет подходящие значения по умолчанию.

Пароль служебной учётки хранится зашифрованным в БД; ключ предоставляется через переменную окружения/Secret отдельно от БД и репозитория. GET сообщает только наличие пароля. Отдельная семантика сохранения старого пароля и его замены. TLS проверяет доверие и имя сервера; для корпоративного CA предусмотрена настройка серверного truststore.

«Проверить подключение» проверяет соединение, bind и поиск, не меняя рабочие настройки. «Сохранить» сохраняет валидную конфигурацию. «Синхронизировать сейчас» запускает синхронизацию по сохранённой конфигурации. Доступна безопасная публичная информация только о доступных способах входа, без параметров каталога.

## Интерфейс

Обновлённая адаптивная форма в стиле FDE: название продукта, краткое назначение, выбор способа входа, подписи полей, показ пароля, состояние ожидания и понятная ошибка. После входа переход определяется доступными страницами; без прав — «О системе». Невалидная сохранённая ссылка не должна обходить проверку прав.

«О системе» объясняет назначение панели: управление потоками передачи файлов, расписаниями и наблюдение за сессиями. Нет фактических данных потоков, счётчиков или административных функций. Сообщение предлагает обратиться к администратору для назначения доступа.

«Настройки» видны только ADMIN, включая состояние загрузки контекста. Внутри пока единственный раздел LDAP. Управление ролями остаётся в «Правах доступа».

## Проверки перед завершением

1. Локальный вход и действующие тесты не регрессируют.
2. Реальный LDAP-протокол в интеграционном тесте: успешный/ошибочный bind, экранирование поиска, неоднозначный пользователь, первый и повторный вход, конфликт логинов, смена логина при стабильном ID.
3. Деактивация, удаление и повторная активация AD; отзыв сессий; ручная блокировка не отменяется. Ошибки/неполные ответы AD не деактивируют пользователей.
4. ADMIN может читать/менять настройки; обычный пользователь не может через UI и прямой API. Секрет не возвращается и не попадает в логи.
5. DWH видит DWH→PC и OFD→DWH, не видит PC→OFD; несколько ролей объединяют область; без области нет потоков. Проверить прямой ID, сессии, расписания и действия, не только список.
6. UI: локальный/доменный вход, переход без прав на описание, назначение роли и изменение доступных страниц, административные настройки и создание новой роли.
7. Сборка backend/UI, профильные тесты и браузерная проверка на стенде. Для проверки реального корпоративного AD потребуются доступность каталога с сервера, его параметры, служебная учётка и доверенный CA; эти значения вводятся в настройки, секреты не коммитятся.

## Границы

Не включаем Kerberos/прозрачный Windows SSO, автоматическое назначение ADMIN из групп AD и импорт всех сотрудников. LDAP-синхронизация управляет идентичностью и активностью; функциональные роли назначаются администратором FDE.
