## Согласованное направление

Добавить «Аналитика» и «Логи» в боковое меню. Статистику получать из существующей PostgreSQL: информация о пайплайнах, сессиях, задачах и обработанных файлах уже хранится там. Подключать внешние серверы Loki через настройки админки. Развёртывание локального Loki, сборщика логов и нового хранилища фактов не входит в эту работу.

Рекомендуемый вариант: агрегаты в backend FDE и графики в существующем UI; поиск логов — через серверный адаптер Loki. Альтернативы — вычислять статистику по логам или встраивать Grafana — не выбраны: первая зависит от полноты и срока хранения логов, вторая усложняет единые права и переходы между сессиями и графиками.

## Что подтверждено в коде

- `PipelineSessionEntity`: pipelineId, startDt, status, errorMessage, replicaId, createdAt, updatedAt. Отдельного finishedAt нет.
- `TaskSessionEntity`: связь с сессией, порядок, typeCode, isDone, createdAt/updatedAt.
- `ProcessedFileEntity`: связь с задачей, fileName, sourceFileName, fileSize, status, errorMessage, createdAt.
- Сессионные статусы: PREPARE, ACTIVE, SUCCESS, FAILED, ABORTED. UI и тесты файлов используют SUCCESS, FAILED, SKIPPED; поле в БД допускает произвольную строку.
- `SessionService.toResponse` объединяет файлы по fileName между всеми задачами без фильтра успешности. Этот существующий итог нельзя переиспользовать как показатель доставленных файлов.
- `AccessScopeService.sessions()` объединяет область клиентов и существующие RLS-ограничения сессий/пайплайнов. Аналитические запросы должны применять ту же политику до подсчёта.
- API пишет JSON-логи с MDC. Есть correlationId; наличие sessionId/pipelineId во всех внешних сервисах не подтверждено.
- Настройки LDAP уже демонстрируют административный доступ и шифрование секретов. Их ключ и конфигурацию не меняем ради Loki.

Существующие таблицы сессий являются источником только для чтения со стороны API. Новые таблицы нужны только для подключений Loki. Изменение модели executor, времени завершения, идентификаторов попыток и сборщика событий — отдельное будущее расширение.

## Интерфейс аналитики

Маршруты: `/analytics` — обзор, `/analytics/pipelines/:id` — поток. В меню раздел «Работа»: Пайплайны, Сессии, Аналитика, Логи. Сохраняется нынешняя светлая/тёмная тема.

Фильтры: период (24 часа, 7 дней, 30 дней, свой), поток, источник, получатель, датацентр. Выбранные фильтры сохраняются в URL, секреты туда не попадают. Для первой версии период ограничен 366 днями, число точек — 400; слишком мелкий шаг автоматически укрупняется с явной подписью.

Карточки: запуски, SUCCESS, FAILED, ABORTED, выполняются/подготавливаются, процент ошибок, успешно полученные/отправленные файлы и объём. Последний запуск и последний успешный запуск — за всю доступную историю выбранного потока, с соответствующей подписью, а не за выбранный период.

Графики:
1. Запуски по часам/дням, составные столбцы по статусам.
2. Полученные и отправленные файлы: две серии количества.
3. Полученный и отправленный объём: отдельный график, без смешивания байтов и количества на одной шкале.
4. Процент ошибочных сессий по времени; точки без завершений отсутствуют, а не равны нулю.
5. Для выбранного потока — количество и объём по отдельным сессиям; подробности доступны по нажатию.

Таблица под графиками: время запуска, поток, статус, полученные/отправленные файлы и объём, сообщение ошибки, «Сессия», «Логи». Серверная пагинация; графики и итог не ограничиваются текущей страницей. Нажатие на интервал или статус графика открывает соответствующий список, сохраняя исходные фильтры. Общий процент ошибок остаётся рассчитанным по всей выборке, а не становится 100% от фильтра «только FAILED».

Полезные дополнительные показатели первой версии: последняя успешная сессия, серия ошибок с указанием рассматриваемого периода, частые сообщения ошибок с переходом к сессиям, успешные сессии без записей файлов. Последнее называется именно «без записей файлов»: отсутствие записей ещё не доказывает отсутствие файлов на источнике.

Нулевой результат, недоступность БД, неизвестные статусы и неполные данные — разные состояния. Графики имеют текстовую сводку/таблицу для доступности. Запросы при смене фильтров отменяются или игнорируются, если устарели; ошибка не заменяет последний успешный результат ложными нулями.

## Точные правила показателей

- Выборка сессий: startDt попадает в полуоткрытый интервал [from, to). Все их файловые показатели относятся к этому же набору сессий, даже если файл обработан после to. Подпись: «по времени запуска сессии», не «сетевой трафик за период».
- Часовой пояс отображается рядом с периодом. Поскольку текущие поля — LocalDateTime без смещения, перед реализацией необходимо проверить фактическую временную зону записывающего сервиса и подключённой БД. Для одного источника задаётся серверная зона `analytics.source-time-zone`; молча считать исторические значения UTC нельзя. В первой версии селектор зоны пользователю не нужен.
- Ошибки сессий: FAILED / (SUCCESS + FAILED) × 100%. ABORTED, PREPARE, ACTIVE и неизвестные статусы не входят в знаменатель, но видны отдельными счётчиками. Нулевой знаменатель даёт null/«нет завершённых сессий».
- Полученные файлы: строки processed_files со status=SUCCESS у задач разрешённых типов DownloadTask. Отправленные: аналогично у UploadTask. DeleteTask не увеличивает ни одну из этих метрик. Типы проверяются по известному перечню, не по произвольному совпадению подстроки.
- Объём — сумма fileSize соответствующих успешных строк. В UI явно говорится «успешные записи операций». Это не гарантированное число уникальных файлов и не объём фактического сетевого трафика с повторными попытками.
- Download и Upload никогда не складываются в один итог передачи. Два успешных Upload одного файла считаются двумя зарегистрированными отправками. Дедупликация только по имени не выполняется.
- Успешная отправка в сессии со статусом FAILED учитывается как успешная запись Upload; ошибка всей сессии остаётся в сессионной статистике. Обратный откат внешней передачи не предполагается.
- Размеры null/отрицательные не превращаются в подтверждённый объём. Ответ содержит счётчик записей с неизвестным размером и признак неполноты. Неизвестные статусы не считаются успешными.
- Ошибки файлов показываются отдельно от ошибок сессий; при расчёте файлового процента используется тот же тип операции и FAILED/(SUCCESS+FAILED). SKIPPED отдельно.
- Длительность, средняя скорость, p95, повторы и пропущенные запуски не показываются в первой версии: для них пока нет подтверждённого полного контракта данных. updatedAt не подменяет finishedAt.
- Тестовые данные отделяются только по явной конфигурации источника/набора тестовых pipeline ID. Имя с префиксом QA не является надёжным признаком. На текущем стенде аналитика помечается как данные тестового стенда с executor-заглушкой; произвольные нулевые/демонстрационные метрики не генерируются.

## Серверная аналитика

Отдельные AnalyticsController / AnalyticsService / AnalyticsRepository в существующем приложении. Read-only агрегирующие запросы к текущим таблицам. DTO графиков не включают содержимое файлов или учётные данные. Запросы не загружают все JPA-сущности и списки processedFiles в память.

Сначала фильтруются разрешённые сессии, отдельно агрегируются файлы до уровня сессии, затем выполняется соединение. Это предотвращает размножение счётчиков сессий при JOIN задач и файлов. Пустые интервалы заполняются нулевыми счётчиками, но не выдуманными процентами. Согласованность сводки и рядов обеспечивается одним read-only снимком для ответа; ответ содержит generatedAt и описание временной выборки.

Предлагаемые API под `/api/v1`:
- GET `/analytics/overview`: сводка и временные ряды по фильтрам.
- GET `/analytics/pipelines/{id}`: показатели потока и временные ряды.
- GET `/analytics/sessions`: страница сессий с агрегатами файлов и теми же фильтрами.

Для первой версии без фонового ETL, отдельного Prometheus и materialized views. Индексы и пределы времени запроса выбираются после EXPLAIN на реальном объёме; добавление индексов к таблицам executor требует учёта владельца схемы. Общего кэша без ключа прав пользователя не вводим.

## Настройки → Подключения Loki

Администратор может добавить несколько именованных подключений, редактировать и отключать их. Пример назначения: SP, SC, тестовая среда. Выбор источника сохраняется при переходе из аналитики; если подходящих подключений несколько — пользователь выбирает явно. Отказ одного Loki не блокирует аналитику БД.

Поля подключения:
- Название, описание, включено/выключено, область датацентров/среды.
- Базовый HTTPS URL с поддержкой префикса reverse proxy.
- Авторизация: без авторизации, Basic (логин/пароль), Bearer token.
- Необязательный tenant для X-Scope-OrgID.
- Базовые метки потоков Loki: например cluster, namespace, application; ввод как пары ключ/значение, не произвольный LogQL.
- Способ корреляции: поля JSON либо structured metadata; имена полей pipelineId/sessionId/taskSessionId/level и необязательного correlationId. Только допустимые имена полей.
- Таймаут запроса (по умолчанию 10 секунд, максимум 30), лимит строк (по умолчанию 200, максимум 1000), ограничение интервала поиска (по умолчанию максимум 24 часа).

Корпоративные CA подключаются через серверный truststore. Проверка TLS обязательна. Пароли/токены хранятся зашифрованными в БД отдельным ключом вне БД/репозитория; GET возвращает только флаг наличия секрета. Пустой ввод сохраняет старый секрет, замена и очистка — отдельные явные действия. Секреты не попадают в ошибки, аудит, URL, браузерное хранилище или логи приложения.

«Проверить подключение» проверяет реальный read API с базовым селектором, а не только /ready: TLS, авторизацию, tenant и возможность выполнить ограниченный запрос. Отсутствие логов — успешная связь без результатов, не ошибка подключения. Настройки не сохраняются автоматически при тесте. Результат содержит время проверки и безопасную диагностическую категорию.

Сетевой адрес задаёт только ADMIN; пользователь поиска не передаёт URL, tenant или произвольные заголовки. Исходящие адреса ограничиваются серверным списком разрешённых хостов/портов; корпоративные внутренние Loki допускаются явной настройкой. Запрещены URL с userinfo/query/fragment, перенаправления на другие адреса и обращения к метаданным инфраструктуры. Тест подключения использует те же ограничения.

## Логи и переходы

Маршрут `/logs`, параметры ссылки: connectionId, pipelineId, sessionId, from, to, level. Форма: подключение, сессия, период, уровень, сервис из разрешённых меток, поиск по тексту. Строка лога: время, уровень, сервис, сообщение; раскрытие JSON и stack trace; просмотр соседних строк с сохранением области доступа.

Для обычного пользователя первая версия работает с выбранной сессией: backend проверяет её через существующую session scope/RLS, строит точный предикат sessionId и повторно проверяет соответствие возвращённых записей. Нельзя расширить запрос до чужих потоков редактированием URL или поисковой строки. Список доступных подключений отдаёт только ID/название/безопасные возможности.

Администратору доступен поиск общих логов по базовой области подключения. Некоррелированные записи доступны только администратору. Подключение без подходящего поля sessionId помечается «нет корреляции с сессиями»; ограниченному пользователю не выдаются общие логи в качестве запасного варианта. Это явное ограничение источника, а не пустой успешный результат.

Из строки сессии автоматически задаются sessionId и интервал от startDt−5 минут. Пока нет достоверного finishedAt, верхняя граница задаётся текущим временем с лимитом интервала подключения; для старой сессии открывается первый ограниченный интервал после запуска и предлагается менять окно. updatedAt не называется временем окончания. Используется явно указанная временная зона источника БД.

Loki вызывается backend через query_range. Поисковый текст экранируется как литерал; произвольный LogQL не предоставляется в первой версии. Логи выводятся как текст, без исполнения HTML/ANSI. У результатов есть отметки «усечено лимитом», «источник недоступен», «нет строк в выбранном окне». Кнопка загрузки следующих строк сохраняет границы и корректно обрабатывает одинаковые timestamps; если полноту такого продолжения гарантировать нельзя, интерфейс просит сузить период и не заявляет, что показаны все логи. Первая версия без live-tail и автоматического объединения нескольких Loki.

## Права и конфигурация

Новые права в существующей системе: page.analytics, api.analytics.read, page.logs, api.logs.read. ADMIN видит всё; остальным назначает администратор. Наличие роли DWH ограничивает область клиентов, но само по себе не заменяет функциональное право. Пользователь без прав по-прежнему видит только «О системе». Проверки выполняются в API, включая списки фильтров, графики, суммы и прямые ссылки.

Управление подключениями и их тестирование — только ADMIN на UI и API. Область подключения дополняет, а не заменяет права на сессию. Изменение подключения записывается в аудит без секрета. Удаление для первой версии заменено отключением: сохранённые ссылки показывают понятное состояние.

## Этапы и критерии приёмки

1. Аналитика существующей БД: проверить реальную схему, статусы и зону времени; реализовать read-only агрегаты, права, обзор, графики и историю. Проверить данные с несколькими задачами, одинаковыми именами, частичными ошибками и неизвестными размерами. Числа совпадают с независимыми SQL-расчётами.
2. Подключения Loki: настройки нескольких источников, отдельное шифрование секретов, тест read API, отключение, таймауты. Проверить 401/403, ошибочный tenant, TLS, пустой результат, предел ответа и недоступность. Интеграционные тесты с управляемым HTTP-сервером; реальную связь проверять после ввода адреса и служебных данных владельцем.
3. Просмотр логов: поиск, раскрытие, переход из аналитики, сохранение фильтров. Проверить чужую sessionId, отсутствие корреляции, попытки расширения запроса, одинаковые timestamps и усечённый ответ.
4. Итог: backend/UI tests, сборка, проверка браузером, адаптивность и обе темы; сверка DWH→PC и OFD→DWH доступны, PC→OFD недоступен пользователю DWH. Секреты не возвращаются и не логируются. Отсутствие Loki не ломает аналитику.

До ввода реального Loki можно полностью реализовать и проверить интерфейс/адаптер на тестовом сервере. Успешное подключение к корпоративному Loki нельзя заявлять по результатам имитации. Действующий стенд и реальные файлы не запускаются ради наполнения графиков.
